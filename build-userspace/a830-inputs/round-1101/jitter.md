# 系统级 jitter 定位报告（round-1101）

运行目录：`工具/gpu-test-loop/runs/20261101-110201-stage15-smoke-1`。文中时间都是日志秒。  
证据等级：【实测】我跑命令或读日志得到；【读码】读 XNU、驱动、共享缓存反汇编得到；【推断】由前两者推出，没有直接观测。

## 0. 结论

1. **调度不是 jitter 的原因。**【实测】启动风暴和键盘死循环之外，前台带 21.7 万次调度只有 1 次超过 10 ms，全部带 76.3 万次调度没有一次超过 50 ms，前台最大 13.9 ms。
2. **`idleq` 是采样假象，不是丢唤醒。**【实测+读码】3011 个 tick 是同一事件被每个空闲核各算一遍，按秒取单核最大值只有 708；70% 的 tick 落在“所有线程最大调度延迟都小于 1 ms”的秒里；10 个 idleq 采样里 6 个当场抓到被选中、IPI 在途的核（`~/0`）；IPI 最慢 0.1 ms，悬而未决 0 次。`stall-report.py` 的那句结论是工具过度解读。
3. **报告里的 gap 大部分不是卡顿。**【实测+读码】统计窗口内 66% 的 `jit`（321/487）来自周期动画，主要是桌面时钟图标秒针：`SBHClockApplicationIconImageView` 用 10 Hz 的 `CADisplayLink`，帧间隔正好 100 ms。窗口内 54 个 gap 采样里 34 个全系统空闲，只有内核线程在核。
4. **真正的卡顿集中在“本次开机第一次做某件事”。**【实测】SpringBoard 主线程同步要渲染服务器做快照（`CARenderServerSnapshot`），渲染线程在 `-[NBCommandBuffer commit]` 里当场编译管线（214.4 s 卡 1 s）或给新表面做 `dc cvac` 时逐页缺页（239 s 两次各约 185 ms）；112.8 s 还有一次 198 ms。这解释了“不可预测”：同一个动作第一次卡，第二次不卡，每次开机重来，因为 Data 是内存盘。
5. **根卷页入与 App 启动是第二大类，GPU 与热是第三大类。**【实测】非启动时段只要这一秒根卷读 ≥50 ms，15 秒里 15 秒出现 >50 ms 的帧间隔。GPU 提交耗时 q≥15 ms 的秒有 24 个，温度 ≥90 °C 45 秒，热限制期间 GPU 被压在 525 MHz、忙度 80–99%。
6. **日志看不见的一类：软件节拍与面板不同频。**节拍固定 120.000 Hz（8333 µs），实测面板 TE 周期 8293–8305 µs（约 120.5 Hz）【实测，只有一次 13 个沿】。由此推出约每 2 秒重复一帧，撕裂线同周期滚动【推断】。这类抖动 FPS 和 ft 都显示完美，而用户说的“流畅但时不时抖一下”和它吻合，但目前没有直接证据。
7. **还有 17% 的活跃秒查不出原因**（有触摸、无 CPU/IO/GPU 证据）。探针在 gap 时不看前台 App 主线程，分不清“屏幕本来静止”和“App 主线程阻塞”。典型是 80.3–85.7 s 设置页：81 s、82 s 各有一段触摸，5.4 秒没有一帧，前 3 秒 CPU 几乎全空闲，84 s 起 `iconservicesagent` 才第一次打开 Metal。这一类必须加探针才能定案。

“完全消灭 jitter”做不到，第 8 节逐条说明；把主要成因修掉、把用户可感知的大卡顿降到偶发，是现实目标。

### 2.3 gap 假阳性怎么分辨（rs W 且 sb W）

**周期动画（确定的假阳性）**

- **10 Hz/100 ms 是时钟图标秒针。**【读码】`+[SBHClockApplicationIconImageView initialize]`（0x1cf4ceafc）算出 `CAFrameRateRangeMake(10 或 8, 120, 10 或 8)`，`-_setAnimating:`（0x1cf442eb4）建 `CADisplayLink` 并设这个范围。
- 【实测】FPS 10、间隔 100.0 ms 的时段是 146–170、189–199、244–275 s；在 App 里的时段是 FPS 0。这说明它只在桌面出现【推断，时钟图标在首屏】。
- 这也解释了桌面上手指停顿时恰好 100 ms 的“卡顿”（63–68、276–278 s）：触摸帧停止驱动后，屏幕上只剩时钟这路帧。
- **500 ms 一组（FPS 9，`gap 500`）**：搜索框光标闪烁，127–181 s 这种样本有几十个；此前已判定为屏幕静止时的周期动画。
- **20 Hz/50 ms（293–294 s）**：定时动画，疑似设置页转圈【推断】。
- 影响：窗口内 `jit` 487 次里 321 次（66%）来自周期秒。`J` 记录和 `gap100` 阈值恰好压在时钟周期上，噪声很大。

### 2.4 真卡顿的证据

**A. 渲染线程同步编译管线**

- 214.4–215.4 s：rs 连续 4 个样本在核，帧间隔 1001 ms。sb 主线程同步卡在 `-[SBHomeScreenBackdropView homeScreenBlurredContentSnapshotImage] → _SBCreateSnapshotBelowWindowWithOptions → CARenderServerSnapshot → CARenderServerRenderDisplayContextList`，等了 1036 ms。【实测】

- 用 dSYM 符号化（UUID 与产物一致）：`metal2vulkan::reflection::linked::writes_depth_unattached → guarded → StageEntries::specialized → pipeline::compile::specialize_one → specialize_request → metal2vulkan_air::specialize_dynamic → canon::…`，214.497 s 落在 Turnip 的 `tu_compile_shaders → ir3_compile_shader_nir → ir3_ra`。【实测】

- 渲染服务器的管线数：51 s 24，131 s 186，211 s 206，291 s 248，371 s 260。【实测】开机几分钟后还在新增，所以这类卡顿会一直零星出现。

- 2026-10 早期记录过同类数字：98 条管线 63 s，单条最长 1.6 s（`CacheExport.h` 注释）。【读码】

**B. 渲染线程在 commit 里给新表面做缓存维护时逐页缺页**

- 239.167 s：rs 在核 120 ms，用户栈 `cleanRange ← runPlan ← cleanSurfaces ← -[NBCommandBuffer commit] ← CA::OGL::MetalContext::flush ← Display::render_surface`，`kpc=_pmap_enter_pte+0x1c4`，`esr=0x92000147`。ISS 的 CM=1、DFSC=7：**是 `dc cvac` 碰到未映射页触发的 L3 转换缺页**。【实测】
- 触发者是 SpringBoard：`-[SBRootFolderView _updateDockBackgroundViewForOcclusionByOverlay] → -[MTMaterialLayer setContentReplacedWithSnapshot:] → CARenderServerSnapshot → CARenderServerRenderDisplayLayerWithTransformTimeOffsetAndFlags_`，sb 主线程同步等了 128 ms。快照要一块新的、GPU 写的表面，正好落进这条路径。【实测】
- J 记录同一段有两次几乎等长的间隔：185.6 ms（238.6 s）和 184.9 ms（239.2 s）。这一秒缺页 2778 次，相当于约一块全屏表面的页数。【实测+推断】

## 3. idleq 是真问题吗（任务 2）

**结论：采样假象。**

**计数口径有放大**【读码】

- `boot_progress_stall_cpu_read` 的 `runq` 是 `sched_clutch_runq_count`：整个 pset 的 clutch 根计数加本核绑定队列；8 个核同一个 pset。所以一个在途线程会让每个空闲核同时计数。
- `stall_watch_cpu` 还把“已被选中但还在 idle 线程上”的核算作空闲。
- 判据只要求连续 2 个 tick（约 11 ms）都看见队列非空，不要求是同一个线程。

**正常路径没有“有空闲核却不派”的分支**【读码】

```
thread_setrun → choose_processor：lsb_first(idle_primary_map) 必选空闲核（sched_prim.c:5389）
 → processor_setrun → sched_ipi_action：目标核置 PROCESSOR_DISPATCHING
 → sched_ipi_perform → machine_signal_idle(_deferred)
 → cpu_signal_internal → PE_cpu_signal(_deferred)
 → IOCPU::signalCPUDeferred 默认转 signalCPU → ArmCpu::signalCPU 写 ICC_SGI1R_EL1
 → ArmCpu::interrupt → cpu_signal_handler_internal → 退出 idle → thread_select 取线程
```

- `CONFIG_SCHED_DEFERRED_AST` 在 bcm2837 配置里开着，但 ArmCpu 没有覆盖 `signalCPUDeferred`，延迟 IPI 就是立即 IPI。
- 空闲核被任何中断唤醒后，`processor_idle` 也会检查 `processor_queue_empty`。

| 10 个 idleq 采样 | 6 个有 `~/0` 核；其余 4 个有刚进 idle 0 ms 的核；全部 `rq=1` |
| 120.6–122.1 s 的 6 个样本 | 这三秒每秒 2.4–3.2 万次调度，最大延迟 10.4 ms，5 tick（约 55 ms）的 streak 不可能是同一个用户线程 |
| IPI | 发 2637023，收 2632038，差 0.19%（SGI 合并）；最慢 0.1 ms，且只有 12 秒达到；悬而未决 0 |

连续 2 tick 看见队列非空，如果是同一个用户线程被晾着，延迟至少 10 ms，M lat 一定看得到。88% 的 tick 所在秒都没有。

**基线计算**【实测+推断】

- 199 个非 idleq 采样里 37 个（18.6%）是“队列非空且有空闲核”。
- 按独立事件算：每秒约 90 tick × 0.186² ≈ 3.1 次，310 秒约 964 次，实际 708 次，**比纯巧合预期还低**。
- 18.6% 对应每次调度平均在队列里约 28 µs（λ≈7400/s，−ln(1−0.186)/λ），与 lat≈0.0 ms 吻合。
- 所以 idleq 量到的是“单次约 28 µs 的正常排队被 11 ms 周期的点采样碰巧撞上”。

**尚未排除**：M lat 只统计用户线程，内核线程的延迟没有直接数据。结合上面的代码路径和 IPI 数据，问题存在的可能性很低。下一轮把内核线程也计入可以彻底关掉。

**工具修正**：`stall-report.py` 现在是 `if stuck or hungry` 就下结论，应改为 `stuck>0`，或“同一秒 lat 超过 2 个 tick 且有 idleq”。

## 5. 空闲内存与根卷（任务 4）

**free 接近 0 本身不是内存不够。**

- 【实测】60–180 s `free` 接近 0 时 `avail` 还有 1.0–2.3 GB，回收的是文件缓存，`cmp`、`dcmp` 全程几乎为 0（压缩器没有干活）。

**但本内核的页面水位偏紧。**

- 【读码】本内核是 4K 页（`vm_page_bootstrap: 1499090 free pages` 对应 5.7 GiB），而 iOS 的水位上限按页数写死：`VM_PAGE_FREE_MIN_LIMIT=1500`、`VM_PAGE_FREE_TARGET_LIMIT=2000`，保留 100+28=128 页。
- 在 16K 页的真机上这是 23/31 MB，这里只有 5.9/7.8 MB，保留 0.5 MB。
- 【实测】`free` 每秒最小值的 33 秒正好是 127 或 128，就是这个地板。低于它时，非特权线程 `vm_page_grab` 返回空，进 `vm_page_wait`。【读码】

**这个地板主要由 Spotlight 跑飞触发。**【实测】36 个 `free≤130` 的秒，34 个在启动风暴和键盘死循环窗口，窗口 T 内只有 112、123 两秒。所以修好键盘循环后，它对日常 jitter 的影响会小很多。

**缺页路径会阻塞吗？**

- 【读码】会，`vm_fault` 拿不到页时走 `vm_page_wait`；另外走 `vm_page_queue_lock` 竞争。
- 【实测】434 个线程样本里 U 状态只有 1 个：179.914 s Spotlight 在 `vm_fault_internal → lck_mtx_lock_contended`，事件 `0xfffffff00c280c48` 是 `_vm_page_locks+0x48`，即页队列锁。rs、sb 没有一次 U，也没有 `hint` 指向缺页。
- 结论：VM 阻塞没有在关键线程上被抓到，但样本只在卡顿时刻取，且没有 `vm_page_wait` 次数统计，不能说完全没有。

**根卷读与 jitter 的重合**【实测】

- 窗口 T 内 rd≥200 ms/s 的秒：110–114、116、117、119、283、284、291、292、297，加上 127、128、178、182、203–206、209、210。
- 非启动秒里 rd≥50 ms/s 全部出现 >50 ms 间隔（15/15）。
- UFS 利用率 ≥50% 的 22 秒里，18 秒在开机 15–32 s。单次读 39–78 µs，高负载时不明显变慢，瓶颈是单槽串行，不是单次延迟。

**内存账**【实测】

- XNU 窗口 6 GiB，开机可用约 5.7 GiB。GPU 池预留 1024 MiB。
- Data 内存盘按写入占 RAM：剩余 1529 MB（15 s）→ 972 MB（125 s）→ 857 MB（365 s），已占约 1.2 GB，其中 467 MB 是每次开机拷的预装应用。
- `avail` 开机 4466 MB，100 s 1890 MB，稳定后约 1500 MB。

## 6. CPU 频率（任务 5）

**结论：频率不是主因，触摸保持 250 ms 和启动提升 1.5 s 目前够用。**

- 稳态够用【实测】：`H` 行显示 d0 在 1774–2902 MHz；231–234 s 无触摸 FPS 120、最大 10–12 ms（1774 MHz）；73–75 s、299–301 s 触摸中 FPS 120、最大 9–12 ms（约 2214 MHz）。
- 启动提升够用【实测】：109–112 s 连开 App，FPS 107–118，最大 26–48 ms；调度延迟都在 25 ms 以内。这几秒的问题是页入和 rs 同步工作。
- 没有证据支持“首帧因频率慢”：探针没有逐帧数据，只有 Q 里零散的触摸到帧时间。治标的调整见 F11。
- 热限制是频率真正掉下来的时候：210.7 s 固件压到 1785/2438 MHz。这是发热问题，不是调频策略问题。

**核迁移**

- 【读码】`choose_processor` 用 `lsb_first`，总从低号空闲核开始。
- 【实测】t≥100 s 的样本里，用户线程在各核的次数：0–7 号分别是 73、80、53、34、15、17、4、14（每核总样本 193）。**4.32 GHz 的 6、7 号大核几乎不用**，UI 线程基本落在 d0。
- 【读码】调频器取“各核自己平均后最忙的核”，线程在几个核之间跳时，单核负载被稀释；有 GPU 帧地板（1785/2649 MHz）兜底，所以没有造成掉帧。
- 【实测】每秒约 7100 次进 idle、7350 次 IPI，每次调度约一次 IPI。开销存在，但没有表现为延迟。
- 让优先级 ≥47 的线程优先落 6、7 号核是可行实验（见 F10），收益不确定，代价是发热。

## 8. 消灭不了的部分

- **第一次使用的代价**：Data 是内存盘时，本次开机第一次开 App、第一次用某个特效，一定有冷启动。F2、F9 只能覆盖预先跑过的路径。
- **GPU 跑不动的场景**：rs 单个作业已经 10–14 ms 的场景（模糊、地图等），在 8.3 ms 预算内做不完，只能降帧或降负载。
- **持续热负载**：SoC 到 95 °C 后 GPU 和 CPU 都会降频，这是物理限制。
- **根卷单槽轮询**：F12 之前，后台大量读和前台页入一定互相排队。
- **没有硬件翻页时的撕裂**：单缓冲拷贝无法完全避免，F7 只能去掉节拍差。
- **iOS 自身的行为**：触摸到第一帧有手势识别延迟（如 378 s 约 150 ms），长按、滚动起步阈值，都不是 bug。
- **诊断本身**：本轮带 `pagani-diag=1`、`sheng-log=1`、36 份日志、面板探针。它们的开销没有单独测过，最后要跑一次全关的对照。
